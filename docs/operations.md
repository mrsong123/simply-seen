# 部署、运行与恢复

## 上线步骤

1. 在可信环境构建Java JAR及网页，确认测试通过。填写根`.env`、网页构建环境及小程序构建环境；所有示例域名换成已验证的真实地址。
2. MySQL8.4创建独立库，启用备份。`DATABASE_URL`应采用证书身份校验；根据实际基础设施配置JVM信任库。禁止使用生产库运行CommerceTest。
3. 私钥、公钥放入只读`secrets/wechat`。首个管理员凭据使用独立随机口令，首次登录后更新密码，并创建财务和第二管理员。所有密钥不进镜像和Git。
4. `docker compose up -d --build`启动。Flyway自动验证/执行迁移；迁移失败不能修改历史校验和绕过。
5. 外层HTTPS代理转发到WEB_BIND，限制管理入口网络访问；只信任已知代理的转发头，公网不能直达应用容器。
6. 微信后台配置request/downloadFile域名、隐私声明、商户关联、支付回调与转账权限。用真实小额交易逐项验证支付、查询、关单、全退、部分退、出款确认及回调重试。
7. 导入真实商品、核对成本和积分/佣金上限。创建规则草稿，另一管理员审批，记录业务/财务依据。分销、月度活动、转账分别启用。

## 健康与任务

`GET /actuator/health`用于容器外内部健康检查；`UP`仅代表服务与数据库可用，不代表微信权限、预算或所有业务健康。数据库持久Outbox每10秒扫描，任务持有120秒租约，多实例重入依赖业务唯一键；失败指数退避最长1小时。

管理后台对账页可查看未完成任务、渠道错误码及工单。超时未知不解除冻结、不更换商户单号。配置类调用前失败可修复后由任务继续；渠道业务拒绝需核对实际商户权限和记录，不得用测试成功覆盖真实结果。

建议外部监控至少覆盖：健康检查、5xx率、数据库连接池、未完成Outbox最老时间、UNKNOWN/CONFIRMING停留时间、待审退款和提现、账本差异、预算占用、数据库磁盘和备份新鲜度。应用已提供业务记录与健康接口；邮件/短信/值班平台的告警路由由部署方在其监控系统配置，不会虚构已发送告警。

## 对账与税款

后台执行对账会重建全部账户余额，并逐笔查询已成功支付、退款和转账的渠道状态及金额。不能确认的记录作为差异，不计为通过。大数据量生产环境应异步触发并在代理上设置合适超时；当前任务在请求内执行，执行中请勿频繁重复点击。手续费、银行入账及税务机关申报还需与商户实际账单核对。

提现单分别记录gross/tax/net，实际出款net，reserved按gross核销。tax代表财务核定预留税款，不是税务机关已收款证明。财务必须完成实际扣缴/申报/凭证归档，并通过差异工单或外部财务系统保留证据。

## 备份与恢复

配置BACKUP_DIR为受控加密存储，执行`./scripts/backup.sh`，它使用单事务mysqldump、gzip完整性检查及SHA-256。定时调度按业务RPO安排，并异地保存至少一份备份。不得将数据库密码作为命令行参数写入进程列表。

恢复前暂停下单、支付写入与出款，保存当前库的独立备份，核验目标环境及备份时间。设置RESTORE_FILE与RESTORE_CONFIRMED=YES后执行`./scripts/restore.sh`，恢复后验证Flyway、账本重建、未完成任务、渠道原单状态与用户余额，再开放流量。RPO/RTO必须以实际恢复演练测量，不能由脚本存在推断已达标。

回滚优先回滚应用镜像；数据库迁移只前滚，变更前备份。已有真实支付/退款/出款事实不因应用回滚而删除。未知状态依旧查原单，避免重复出款。

## 当前工程的边界

物流支持发货、运单展示和配置后的快递100轨迹查询；电子面单及发票平台连接不在当前商户接口范围。客服采用可配置联系方式和订单售后记录。真机弱网、微信审核、生产负载、安全评估与备份恢复演练属于实际部署验收，必须保留证据。文档中的上线标准不会因代码构建通过而自动满足。
