# 架构与一致性

`mini`为uni-app微信小程序；`web`为Vue3/TypeScript商城与后台；`server`为Spring Boot模块化单体。业务模块分别是Auth、Commerce、Finance、Wechat、Jobs与Api。数据库迁移是唯一建表入口；初始化仅创建首个管理员和规则，演示商品严格受APP_DEV_MODE控制。

MySQL是真实来源。ID由数据库独立事务分配号段，各实例使用不同号段，重启不依赖进程时钟猜测唯一性。所有货币都是人民币整数分，积分是整数点。服务端重查SKU价格、成本、库存、商品资格；客户端传来的价格不会成为计价依据。购物袋、地址、报价、订单、账本和会话均持久化。

## 状态

- 订单：CREATED → PAID → SHIPPED → COMPLETED；未付关闭为CLOSED，全退为REFUNDED。部分退款保留独立履约状态，通过cash_refunded与退款单体现。
- 支付：INIT → PREPAY → SUCCESS / CLOSED；渠道不确定时保留非终态，只查询原单。前端成功回调不能确认PAID。
- 积分：可用积分 → points_held → 成功核销；关闭则反向释放，所有步骤带唯一账务事件。
- 退款：REQUESTED → REVIEWED → PROCESSING → SUCCESS；驳回CLOSED，异常ABNORMAL。未明确成功不冲回资产。
- 佣金：PENDING → SETTLED；全额冲回REVERSED。每订单每级唯一。
- 提现：REVIEWING → APPROVED → SUBMITTED → UNKNOWN / CONFIRMING → SUCCESS / FAILED；审核驳回REJECTED。
- 规则：DRAFT → ACTIVE → ARCHIVED；创建人与审批人必须不同。

## 事务与幂等

创建订单锁会员和按SKU排序的库存，在同一事务中校验报价、生成订单快照、预占库存与积分、消费报价。幂等范围为会员+操作+请求键，相同内容返回原响应，不同内容409。支付确认、退款入账、出款核销各自持有业务记录锁，账本唯一事件键保证只发生一次。错误并发更新返回409，调用方保留原幂等键重试。

外部HTTP调用不属于数据库事务。支付意图先持久化再请求微信；关单前查原单并由微信关闭成功确认，不能凭本地超时当作未支付。取消与支付成功竞争同一订单锁。退款和转账使用持久Outbox、120秒租约与指数退避；未知提交只查原单，不换业务单号重发。配置/密钥签名类的调用前失败可在修复后重新提交同一编号。未知状态保留冻结。

## 认证与安全

微信code由服务端换openid，已有账号不重新绑定邀请；管理密码BCrypt，独立账号三角色。会话只存SHA-256摘要，会员停用撤销会话；每个资源查询校验归属。限流记录独立事务提交，错误密码不能回滚限流计数。生产要求HTTPS外部端点，私钥仅从文件读取，平台序列号匹配、RSA签名、300秒窗口、AES-GCM认证解密，并交叉检查商户、AppID、币种、金额和付款人。平台公钥采用固定公钥ID/序列号模式，轮换需更新配置并重启验证。

账本只追加，后台没有直接写余额接口。管理审计记录账号、动作、资源、依据和时间，不存口令或商户密钥。数据库账号和备份权限应由部署方限制，应用层审计不能替代数据库防篡改及归档控制。

## 与原文档的明确变化

1. 二级成交分销替代一级邀请和80%消费解锁奖励。
2. 初始消费赠分为每满100元赠10分，而非100分；防止默认积分面值负债与毛利预算失配。
3. 使用JdbcTemplate和数据库会话/限流/租约，替代MyBatis与Redis依赖，降低初期部署复杂度。
4. 积分过期未作为初始产品规则；积分不自动到期。未来变更需公示与版本审批，不能追溯删除账本。
5. 月度优惠采用已明确的排名优先、剩余预算可部分奖励方式。
6. 真实税额由财务审核录入，不提供未经商户税务主体确认的自动申报或猜测税目。
